## 2. 목표와 평가 범위

기준 상대 `T`는 이번 캠페인 시작 시 등록된 9개 원본 모델 중 대전 성과가 가장 좋은 모델이다. 모든 조합을 비교하되, 상위권의 직접 대전과 선후공별 결과를 함께 본다. 순환 우열이 나오면 하나의 보편적 최강이라고 주장하지 않고, 관측된 리그 선두를 주상대, 나머지 상위 모델을 보조 상대로 지정한다.

상대를 정한 뒤에는 `T`의 코드·가중치·설정을 고정한다. 후보를 개선할 때마다 상대까지 바꾸지 않는다. 원격에 새 모델이 추가되면 현재 캠페인과 분리한 다음 캠페인에서 상대를 다시 선정한다.

기준 도전자 `C0`는 `T`를 제외한 기존 모델 중 `T`에 가장 좋은 성과를 낸 모델이다. 최종 후보 `C*`는 같은 조건에서 `C0`보다 높은 승률을 목표로 한다. 추가로 상위 보조 상대를 만나 특정 상대에만 맞춘 성능 편중을 확인한다.

이 프로젝트의 승률은 제한된 상대·규칙·시작 조건·계산 예산에서 측정한 값이다. 전역 최적 모델이나 반드시 이기는 모델을 보장하지 않는다.

## 3. 고정할 규칙과 실험 조건

- 규칙은 `twelve-janggi-strict-v2`, 모델 계약은 `js-v1`이다. 기존 심판과 `src/engine.js`를 사용한다.
- 왕 포획 금지, 자기 왕 안전, 안전한 왕 진입 즉시 승리, 체크메이트/착수 불가 패배, 상대 끝줄 포로 투입 금지를 유지한다.
- 같은 국면 3회 반복과 모델 배치 256수 도달은 무승부다. 체크메이트 등 기존 종국 판정이 우선한다.
- 본 대전은 임의 오프닝 0수, 착수당 실행기 제한 60초, 동시 2국이다.
- 청/홍과 초기 차례 네 조합을 같은 비율로 배정한다. 웹 100국은 각 조합 25국이다.
- 모델 오류·불법수·잘못된 응답·시간 초과는 해당 모델의 패배다. 인프라 오류·외부 취소는 미완료로 분리한다.
- 모델 내부 rollout의 중단을 실제 대국의 무승부로 집계하지 않는다.

두 시간 조건을 별도로 비교한다. **원본 등록 설정 대전**은 실제 현재 모델의 성과를 측정한다. **동일 계산 시간 비교**는 알고리즘 변경과 시간 증가의 효과를 구분한다. AlphaZero는 횟수 기반이므로 실제 착수시간 분포를 측정하고, 단순히 같은 60초 실행기 상한이라는 이유로 계산량이 같다고 해석하지 않는다.

## 5. 후보를 개선하는 순서

### 5.1 계산 설정의 효과부터 측정

원본 성과와 실제 소요시간을 본 뒤 유망한 계열에 집중한다. 예를 들어 StockJang은 시간·노드 한도를, Team Minimax는 깊이·시간을, AlphaZero는 탐색 횟수를 바꿀 수 있다. 한 번에 하나의 주요 변수를 바꾸고, 시간 증가만으로 좋아진 후보는 그 사실을 명시한다. 모든 한도의 곱을 전수 시도하지 않는다.

신규 후보 예시 ID는 `lab-stockjang-v1`, `lab-stockjang-v2`, `lab-azero-v1`이다. 실제 등록 시 사용한 설정을 manifest에 고정한다. 예시 ID가 이미 구현됐다는 뜻은 아니다.

### 5.2 패배 기보로 개선 가설 수립

패배를 왕 진입 방어 실패, 전술적 기물 손실, 포로 활용 실패, 반복 유도/회피, 탐색 깊이 부족, 실행 오류로 나눠 확인한다. 탐색 점수가 처음 달라진 수와 대안 수를 실제 재탐색해 원인을 확인한다. 모든 패배를 평가 함수 탓으로 단정하지 않는다.

그 결과에 따라 왕 진입 위협·포로 가치·전술 수 정렬·안정화 탐색·MCTS rollout 정책을 후보별로 수정한다. 공통 helper를 바꾸면 영향을 받는 기존 모델까지 변하므로 후보 전용 새 helper 파일을 사용한다.

### 5.3 학습은 별도 후속 실험

대국 반복 자체가 모델을 학습시키지는 않는다. 이번 1차 실행은 원본 가중치를 보존한 설정·탐색 개선으로 시작한다. 학습이 필요한 근거가 확보되면 `train/`의 자기 대국/학습 과정을 별도 출력 경로에서 실행하고, 새 가중치의 해시와 새 버전을 등록한다. 최종 검증 기보는 학습에 사용하지 않는다.

## 6. 통계와 후보 채택 기준

완료 대국 수 `N=W+D+L`에 대해 주지표는 `W/N`이다. 무승부를 제외한 승률을 기본 승률로 사용하지 않는다. 보조 지표는 `(W+D/2)/N`, 패배율, 선후공/진영별 성과, 실제 착수시간 평균·p95·최대값, 모델 실패 횟수, 서로 다른 기보 수다.

후보와 기준 도전자의 `T` 상대 승률 차이를 %포인트로 표시한다. 탐색 점수와 AlphaZero/MCTS 내부 값을 실제 대전 승률로 표시하지 않는다. 미니맥스의 완료 깊이와 MCTS의 방문 깊이도 같은 지표로 직접 비교하지 않는다.

결정론적 모델끼리 고정된 네 시작 조건에서 같은 수순을 100번 반복해도 독립 표본 100개가 되지 않는다. 이 경우 결과는 네 조건에서 관측한 승무패와 수순의 재현성으로 설명한다. 확률적 대국의 불확실성을 계산할 때만 시작 조건별로 나눈 독립 seed 묶음을 사용한다. 시간 제한으로 인한 기기 부하 차이는 별도로 기록한다.

후보는 다음 조건으로 채택한다.

1. 입력·규칙·실행 계약 검증과 기보 재검증을 통과하고 모델 실행 실패가 없다.
2. 고정 상대에 대한 별도 검증 성과가 기준 도전자보다 개선됐다. 개선이 불확실하면 잠정 후보로 남긴다.
3. 보조 상대와 전술 회귀 결과에 중대한 퇴행이 없거나, 특정 상대 전용이라는 제한을 분명히 적는다.
4. 계산 시간 증가, 중복 수순, 검증 표본의 한계를 포함해 보고한다.

탐색 중 최고값을 고른 결과를 그대로 최종 증거로 쓰지 않는다. 최종 후보를 고정한 뒤 새 seed/별도 기보에서 검증하고, 검증 후 수정했다면 새 후보로 취급한다. 관측 승률이 50% 이하이면 개선 여부와 별개로 '상대보다 우세' 목표는 미달이라고 기록한다.

## 7. 웹에서 계속 실험하는 운영 방식

현재 앱은 모델 두 개 선택 → 100국 추가 실행 → 동일 조합 누적 → 수별 기보/시간 확인을 지원한다. 같은 조합의 A/B 순서를 바꿔도 결과가 합쳐진다. 따라서 실험 결과를 계산할 때 화면상의 A/B가 아닌 모델 ID와 실제 진영을 기준으로 한다.

이번 실행은 기존 앱의 게스트·Origin·CSRF 검사를 거치는 API로 배치를 제출하고, 기존 `/experiments` 페이지에서 결과를 보여준다. `GET /api/models`, `POST /api/model-matches`, 조합 상세 및 개별 기보 조회를 재사용한다. 제출 본문에는 현재 허용된 `modelA`, `modelB`, `requestId`만 넣는다. seed나 임의 국면을 웹 API에 전달할 수 있다고 가정하지 않는다.

동일 게스트에 진행 중인 대전이 있으면 새 제출이 거부되므로 한 배치를 확인한 뒤 다음을 제출한다. 요청 재시도에는 동일 `requestId`를 재사용해 중복 배치를 방지한다. 캠페인 로그에는 반환된 배치 ID와 실제 실행 버전을 저장한다.

모델 registry는 서버 시작 시 읽힌다. 후보를 여러 개 완성한 뒤 함께 등록·검증하고, 진행 중 배치를 마친 다음 정상 재시작해 반영한다. GitHub에 push하는 것만으로 실행 중인 페이지의 모델이 교체되지는 않는다.

브라우저를 닫아도 서버가 대국을 계산한다. 연속 배치 제출은 로컬 실행 스크립트가 담당하며, 배치·후보·시간 예산 한도와 체크포인트를 갖는다. 일시 중단은 새 배치 제출을 멈추고 현재 진행 상태를 보존한다. 외부 터널이 끊겨도 로컬 DB와 서버 작업은 별개로 보존한다.

추후 화면에 캠페인 시작/중단·상대 고정·후보 순위·승률 변화·실패 기보·새 후보 등록 대기 상태를 추가할 수 있다. 이 화면 확장은 현재 대전 기능으로 1차 실험을 진행한 뒤 우선순위를 정한다.

## 8. 기록, 재현, 결과 보존

모든 실험은 원격 커밋, 엔진/모델/helper/가중치/config 해시, Node/OS, seed, 시작 조건, 시간·노드 제한, 실제 시간, 실행 실패, 원본 기보를 남긴다. CLI 결과는 `artifacts/<run-id>/`, 캠페인 요약은 `artifacts/winrate-campaign/`, 웹 대전은 별도 SQLite에 보존한다. CLI 통계를 웹의 기존 조합에 임의로 합산하지 않는다.

CLI의 기본 임의 오프닝은 4수이므로 본 대전에는 `--opening-plies 0`을 명시한다. CLI 스케줄은 웹과 실행 순서가 다르며, 최종 실제 웹 배치 결과는 따로 기록한다. AlphaZero의 절대 256수 한도를 넘는 입력을 만들어 오류 패배를 유도하지 않는다.

기존 ID의 코드·설정·가중치를 덮어쓰지 않는다. 원본 `.env`, 운영 DB, 과거 기보는 변경하지 않는다. 실험 DB와 기보는 `.gitignore` 대상이며 결과 보고서에 필요한 요약만 별도로 남긴다. 작업 브랜치는 로컬에 만들며 원격 push/병합은 별도 배포 작업으로 다룬다.

실행 시간을 먼저 보장하지 않는다. 초기 대전의 초당 완료율과 평균 착수 수를 측정해 남은 대국 수/처리율로 예상 시간을 갱신한다. 같은 장비에서 대규모 학습과 공식 대전을 동시에 실행하지 않는다.
